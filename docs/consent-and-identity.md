# Consent and Identity

## Consent Model

Market Layer integrates with the Shoper Customer Privacy API. The adapter subscribes to four consent callbacks:

- `onAnalyticsConsentGranted`
- `onMarketingConsentGranted`
- `onFunctionalConsentGranted`
- `onPlatformConsentGranted`

It also listens for `consentsService.saved` to capture consent withdrawals. These are independent dimensions, not a single bit.

The adapter maps them to its own state:

```js
state.consent = {
  ready: true,
  analytics: true,   // analyticsConsent
  marketing: true,   // marketingConsent
  functional: true,  // functionalConsent
  platformAnalytics: true
};
```

### Google Consent Mode

Whenever Shoper consent changes, `syncGoogleConsentMode()` updates the `crossborderGtag` consent state:

```js
crossborderGtag("consent", "update", {
  analytics_storage: state.consent.analytics ? "granted" : "denied",
  ad_storage: state.consent.marketing ? "granted" : "denied",
  ad_user_data: state.consent.marketing ? "granted" : "denied",
  ad_personalization: state.consent.marketing ? "granted" : "denied"
});
```

The adapter initializes Google Consent Mode with `default` denied values before consent is known. This ensures no cookies or tags fire prematurely.

### Consent-Gated Delivery

Every delivery function checks consent before sending:

- GA4 browser and server: requires `analytics_storage: granted`
- Google Ads browser: requires `ad_storage: granted`
- Meta Pixel browser and Meta CAPI server: requires `ad_storage: granted` + `ad_user_data: granted`

If consent is denied, the delivery is recorded as `skipped` with reason `analytics-consent-denied` or `marketing-consent-denied`.

### Consent Replay

The initial page view is often captured before consent is known. The adapter stores the first `page.viewed` and replays it after consent grant if it was previously blocked. Replay is tracked separately for analytics (GA4) and marketing (Google Ads + Meta) groups so that granting one consent dimension does not cause a duplicate delivery for the other.

## Event Identity

### event_id

Generated by `createEventId()` using `crypto.randomUUID()` with a timestamp+random fallback. The same ID is attached to:

- The normalized event object (`normalized.eventId`)
- The Meta browser event (`meta.event_id`)
- The server envelope (`eventId`)

This shared ID is the foundation of browser/server deduplication for Meta CAPI.

### transaction_id

For `purchase` events, `transaction_id` is derived from `body.orderId`. It is used as:

- GA4 `params.transaction_id`
- Google Ads `params.transaction_id`
- The primary key for GA4 browser purchase deduplication (`sentPurchases` Set)

## Browser/Server Deduplication

### Browser (GA4)

An in-memory `sentPurchases` Set tracks `transaction_id` values already sent in the current page session. Before sending a `purchase` event via `crossborderGtag("event", "purchase", ...)`, the adapter checks:

```js
if (sentPurchases.has(transactionId)) {
  return noteGa4Delivery(normalized, "skipped", "duplicate-purchase");
}
sentPurchases.add(transactionId);
```

This prevents duplicate GA4 purchase events if the same order confirmation is revisited via browser back/forward.

### Server (D1)

The Worker uses `INSERT OR IGNORE` on the `event_claims` table with a composite key `${marketKey}:${eventId}`. If the event was already claimed, the Worker returns HTTP 202 with `duplicate: true` without forwarding to destinations.

On delivery failure (any destination returns non-OK), the Worker releases the claim:

```js
if (deliveryFailed) await releaseEvent(env, claim.key);
```

This allows a retry on the next request. The release only happens after both GA4 and Meta have been attempted, so partial failures are retried as a unit.

### Meta Cross-Channel Deduplication

Meta uses the shared `event_id` to deduplicate browser Pixel and server CAPI events. The adapter ensures both channels receive the same ID for the same logical event.
